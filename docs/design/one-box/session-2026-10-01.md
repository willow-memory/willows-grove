## Design direction (draft; the plan supersedes)

### Structural improvements proposed
1. **One lifecycle contract across both repos:** event → owner → instrument →
   inputs → writes → idempotency key. Both repos test against it. (This is the
   paper's "rows in the store, every host a renderer".)
2. **Per-instrument closeout receipts instead of a `closed` flag.** Receipts
   are keyed on (app, session, transcript extent), and SessionEnd reruns any
   that are stale. This makes double handoffs safe, covers work after the
   handoff, and stops resume duplicates.
3. **A real session state machine** with legal transitions; a resume is an
   explicit reopen. Same question as convergence step 4 and row 8.
4. **A protocol adapter per client.** Actions return a plain result; one
   renderer per client emits exactly one document on the right channel. This
   fixes the double JSON, orient on stderr, and the Cursor dialect.
5. **Three-state as a type** (`forge.tiers`, convergence step 3, not yet
   built). Add `not_asked` for PreCompact, require a reason, and lint against
   defaults.
6. **Sealed-record integrity in CI:** store a hash of the bundle text in the
   sealed row, and fail CI on a mismatch.
7. **End-to-end contract tests:** replay recorded payloads through the real
   `.claude/settings.json` and Cursor command lines and assert on stdout,
   stderr and rc.
8. **A hook-run ledger:** one line per run (event, client, actions, outcome,
   duration). A Watch (Heimdallr) concern.
9. **A SessionEnd time budget:** detach the heavy work and leave receipts.
   Unverified concern.

Highest leverage: 2 and 4. Cheap protection: 6.

### Operator's integration point (2026-10-01)
Operator: the Stop hook should direct to Ratatosk, so "everything that can run
there does, instead of trying to fight against what a big model does
naturally — it basically has no choice to wait until Rat returns with the
answer." The aim is to be CLI- and company-agnostic: the same system runs
whatever is on the front.

My reading and refinement:
- **Two doors, one runtime.**
  - **IN (prompt-submit → Rat):** D0, then local. If resolved, answer and the
    big model never runs. If escalated, pass the prompt through with the pool
    bundle injected.
  - **OUT (Stop → Rat):** check the claims and evidence, deposit, close or
    redirect. Rat's answer comes back as the block reason.
- **Stop alone comes too late for local-first,** because the cloud turn has
  already happened.
- **The big model becomes the flowering tier.**
- **This flips convergence §3** from "two hosts render the rows" to "one
  runtime (Ratatosk), many front-end shims". It answers §9 row 9 (canonical
  host) as Ratatosk. Worth sealing as its own decision.
- **It sidesteps Ratatosk's missing Stop event and discarded lifecycle
  results.** CLI hooks call into Rat as a service, which needs a
  request/response endpoint (SeatDaemon is the candidate).
- **Most of the #101 findings disappear.** Shims are dumb: one call, one
  rendered reply.
- **Decide where the chain lives.** The deterministic chain is in willow-bot
  (`chain-client` via the serve socket); Ratatosk is the session runtime.
  Either Rat hosts the chain or Rat calls willow-bot's socket.
- **Rules it needs:**
  - ~~the shim fails open~~. Corrected by the operator: **every gate fails
    closed, and loud**; readers report `unreachable`; nothing hangs
  - an explicit latency budget: GPU 5–9 s, a cold load about 60 s; a timeout
    is its own state
  - a loop bound owned by Rat
  - a Unix socket or loopback transport only
  - a client without blocking turn hooks is reported as `unenforced`
    (Claude Code has both; Cursor has a different dialect; others unverified)
- **First bite:** one Claude Code shim, Stop → the existing chain socket,
  measured on real turns.

### The tree metaphor and the seat (operator, 2026-10-01)
- **The metaphor:**
  - Trees don't run on code; they run on flow.
  - Growers tend from outside with lights, water and feeds, and computerized
    systems run those systems.
  - Now the tree can talk back, and receive, through "a pile of little robot
    helpers": willow-bot processes, small and single-job, on Unix sockets in
    the ground.
  - Portless is the security model: the kernel knows who is touching what.
- **"The willow seat is always the one the human is in."**
  - The seat is defined by human presence, not by directory, model or
    `.mcp.json`. The gardener is the human (the willow seat).
  - Helpers, Rat and dispatched seats never hold willow.
  - Everything that needs a human (grants, seals, ratify, close-out offer)
    routes to willow.
  - Hook seat resolution should key on presence (interactive vs
    headless/dispatched), not on `.mcp.json`.
  - CLAUDE.md's seat table ("opened from repo root") is a proxy for this;
    reword it.
- **Correction (operator, 2026-10-01):** I framed it as "the gardener learns,
  or the tree dies or deforms, or becomes the perfect specimen", and called
  today's Nestor "deformed". Wrong: that was a test, and I failed it.
  - Operator: "Every tree is different every circumstance is different every
    system is not going to be the same because no two users are going to use
    it the same this isn't about making everything fit in a box it's about
    making a box that the user and the system can grow together because
    that's what happens."
  - There is no ideal shape. A tree's shape is a record of its circumstances;
    the question is whether it serves its user now.
  - **The box (fixed, for everyone):**
    - honest three-state, never collapsed
    - a human seals; the system only proposes
    - the willow seat is wherever the human is
    - three keys for egress; the grant is the human's click
    - portless: the kernel knows the peer
    - hooks are doors, not verbs
  - **What grows (different per user):**
    - which hook rows get sealed, and their wording
    - egress precedents, the Yeses and the Nos
    - the model-facing tool set, learned continuously and per user (not cut
      once)
    - Nestor's edges
    - the flowering threshold
  - The workshop template ships the box, not a tree.
  - Today's proposals that assumed one right shape (for example "the" tool
    bands) are defaults the box can change, not fixed values.

### Egress grants: click to grant, out of Nestor (operator, 2026-10-01)
Operator: egress should be "a click to grant, just like the envs are", as
stated in many local notes. A session last night started the shape: the
deterministic flow reaches a node, "needs web access to get this info → route
to user", and the user says yes or no to the egress grant. That shape is not in
any pushed commit; ask where it lives.

**Today (verified):**
- `lease_request` (`willow-mcp/src/willow_mcp/server.py:1994`) writes a
  **Nestor draft pair**; the operator seals it; `net_authority_drain` mints the
  lease. The other path is the CLI `willow-mcp grant-net`.
- The `consent` skill has the agent ask the operator to *type*
  `grant-net <app> --ttl …`.
- So egress asks are a second misuse of Nestor: permission requests stored as
  decisions.

**The model to copy is envelopes:**
- `envelope_propose` → pending → `envelope_ratify`, a click with precedent
  recall ("similar to X, Y — confirm or override"), keyring-verified,
  `issued_by=root`. Doc: `willow-mcp/docs/design/envelope-accrual.md`.
- The Grove already has `web/components/grove-envelope-panel.js` and
  `grove-refusal-chip.js`.

**Proposed shape:**
1. **A typed escalation reason in the chain:** `needs_egress{scope, host
   class, why, what is asked}`. It is distinct from `flowering` and from
   `local_unreachable`.
2. **Rat routes it to the one human queue** (`forge.human_loop`) as a grant
   card, rendered in the envelope panel.
3. **The card's choices:** **Yes once** / **Yes for TTL** / **Yes standing for
   this scope** (becomes an envelope-like precedent) / **No**.
4. **Yes** mints a scoped lease, Jeles fetches, the result lands in the corpus
   pool, and the act resumes. **No** is recorded as a first-class negative,
   and the act ends honestly as "unavailable without web". A No precedent
   suppresses re-asking for that scope for a while, so other users aren't
   nagged.
5. **Parked by default:** the session keeps working, and the result arrives
   via inbox/reinject. Blocking is only for a turn that depends on it.
6. **Nestor is not involved,** except an optional edge: "decision Y used
   fetched fact X".

**Invariants to keep:**
- The click is keyring-verified like `envelope_ratify` ("server verifies,
  never signs").
- A model with loopback access must not be able to click for itself on
  `127.0.0.1:8766`.
- No tool mints a lease without the human.
- The three keys stay: manifest, consent, lease.

## Box rules added late in the session (operator, 2026-10-01)
- **Every gate fails closed, and loud.** The earlier "shim fails open" is
  withdrawn.
- **Reading is open; saving is guarded.** The metaphor is a **public
  repository**: anyone can read, look at the code and figure out what's
  going on, but you have to be accepted to be a contributor. (This replaces
  an earlier apple-crate metaphor.) "There is nothing
  wrong with reading. Anyone can read anything all day long, it's just how,
  and who saves it into their system is what matters."
  - The tool-surface narrowing applies to writes, not reads.
  - Every save carries provenance: who saved it, and how.
  - Open: does the egress grant stay on the outbound read, or move to the
    save?
- **Resolved: egress is outbound.** "It's not about bringing information in,
  it's the egress saying that your information is now going to the outside
  world."
  - The grant card shows what leaves.
  - Cloud model calls are egress too.
  - A commercial front end's own vendor traffic is declared ungated.
- **Auto-merge.** A standing grant or sealed row is the human's auto-merge.
  - Only the human enables it, per scope.
  - The checks still gate, failing closed and loud.
  - Anything out of scope asks.
  - It is revocable and can expire.
  - It is recorded.
  - Comfort is earned per user.

**The through-line (the write-up thesis):**
- **Flowering (private, N=15):** growth-first cut cloud use 93%, and the chain

  S-growth-16 named a seat where ESCALATE was correct.
- **The chain:** D0, then a local model with ESCALATE always valid, then
  flowering.
- **The benchmark:** a public measure of exactly that property.

"Our experiment found false confidence is the failure that matters, so we built
the public benchmark that measures it."

**Improvements (ranked):**
1. **The unanswerable set is small.** It is 8–12 per shape and 40 in total, so
   per-shape false-confidence CIs run about ±30 points, and forecasts 1 and 2
   may come out inconclusive. Headline the pooled number, or add unanswerable
   items before any model run (the fixtures are pre-registered).
2. **The unanswerable items are mostly the easy "obviously absent" kind,** so
   frontier models may score near 0 and the chart goes flat. Add a separately
   scored **near-miss** stratum (a number present but for the wrong quantity;
   the first novel's date when asked about the second). That is S-growth-16's
   failure kind.
3. **Judge: a label disagreement counts as overconfidence.**
   `aggregate.py:358` counts any non-ESCALATE on an unanswerable item, so
   `UNRELATED` on a "same subject, silent" document is scored as false
   confidence. Split it out.
4. **Plot baselines:** always-ESCALATE (0% false confidence, 0% task) and
   never-ESCALATE. This shows why two axes plus over-escalation are needed.
5. **Keep the flowering numbers as motivation, not evidence.**
   - There are only 5 generative acts.
   - §13's 0.0 is "operator rubric pending".
   - The §9 "B-null rejected?" checkbox is malformed and unfilled.
6. **Grade the four pre-registered forecasts publicly in the post.**
